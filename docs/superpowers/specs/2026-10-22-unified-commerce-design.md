# Unified catalog and commerce design — merchandise first

**Date:** 2026-10-22. **Status:** S1a merged/deployed by explicit owner approval via PR #49 (`b358f658`); catalog/checkout flags remain off. The owner subsequently requested the S1b checkout plan/recommendations for review. Owner subsequently approved S1b native implementation with preservation and self-review before merge. Trading, payment/booking activation and further merge/deploy remain separately gated.

**Binding direction:** [marketplace roadmap §5](../marketplace-roadmap.md). One Shop/StoreListing catalog, shared commerce, type-specific availability/fulfilment; merchandise first; preserve venue features. This is a native Laravel/Inertia/React extension with no new dependencies. Proposed defaults below are design recommendations, not newly agreed commercial terms.

## 1. Scope and delivery boundary

The target is one branded organisation storefront offering purchases, rentals, venues and services. The first implemented transaction type will be physical merchandise. S1a provides catalog publishing and visibility; S1b adds durable orders/reservations/payment integrity; S1c adds collection and pilot acceptance. Each slice follows the approved design and a scoped plan; the owner has authorised native merchandise implementation and systematic roadmap continuation, with release/trading approvals separate. No speculative rental/service engine, mixed-type checkout, multi-seller basket, pre-order, digital licensing, shipping integration or bulk legacy-booking conversion in S1.

An association can use this with no dues and, for public merchandise, without Community being enabled. Member-only products use existing verified email/member access. Following, staff employment, a phone match, a guest registration and membership are different credentials.

## 2. Common architecture

- **Catalog:** `Shop → StoreListing` is canonical. Keep existing listing identifiers/slugs and `listing_kind` values (`venue`, `rental`, `service`, `merchandise`). Type details are child records, not a competing Product catalog. A microphone for sale and a microphone for hire may be separate offerings with explicit transaction modes; combining those modes on one record is not required for S1.
- **Commerce:** future `StoreOrder` header and `StoreOrderLine` concepts hold seller, verified buyer, currency, immutable item/options/quantity/price/terms snapshots and a stable order reference. `StorePaymentAttempt` is separate from order and fulfilment state. Payment/refund/reconciliation orchestration is shared; existing venue records connect by a stable source reference through an approved adapter later.
- **Availability boundary:** a typed offering answers availability, reserves, releases and fulfils using the applicable rules. Purchases use variant inventory; rentals use quantities/assets across overlapping time windows; venues use their existing authoritative calendar/capacity/approval; services use provider/resource scheduling and agreed scope. This contract is specified now; implement only the purchase adapter in S1b.
- **Fulfilment:** purchase collection/delivery, rental handover/return/condition, venue occupation/inspection and service deliverable acceptance have their own state transitions. A paid order does not imply collected, returned or completed.
- **Common commercial rules:** immutable checkout terms, verified provider/account/reference, expected currency/amount, callback/webhook idempotency, extra/late capture reconciliation and LedgerService-only posting. No fake Event record to make an event-only fee resolver accept a purchase.

## 3. S1a data and publication

These are proposed names/interfaces to make the first implementation plan concrete; later money tables are not created in S1a.

- `StoreMerchandise` (`store_merchandise`): unique listing FK, `visibility` (`public` or `members`), `currency` (`GHS` initially), nullable `archived_at`, collection instructions. Parent remains `listing_kind=merchandise`; existing venue rental-price/capacity fields are not used as sale prices. Preserve existing parent status vocabulary (`draft`, `published`, `suspended`); archive is a merchandise detail state. Platform takedown remains authoritative.
- `StoreVariant` (`store_variants`): listing/seller relation, seller-unique SKU, canonical option key, option labels (size/colour), integer `price_pesewas`, nonnegative integer `on_hand`, active state. A simple item has one default variant. SKU/canonical-option uniqueness is enforced at database level. For S1, SKUs are trimmed uppercase ASCII letters/digits/hyphens/underscores, maximum 64 characters. For the canonical option key, trim/collapse Unicode whitespace and lowercase each option name/value using existing multibyte helpers, reject duplicate normalized names, sort by normalized name and hash the canonical JSON; retain original display labels. Test case, whitespace and input-key order equivalence. Do not hard-delete variants once referenced by commerce; archive/deactivate them instead.
- `StoreStockMovement` (`store_stock_movements`): append-only variant delta, reason, actor ID/name snapshot and timestamp. Preserve this audit if a user account is deleted; verify the actor through the authorised inventory service when writing, rather than blocking account deletion with a live-user FK. S1a handles manual receipts/corrections through a locked inventory service; it does not create customer reservations. Stock corrections never take on-hand below zero. Each adjustment has a UUID idempotency key unique per variant; retrying the same payload returns the original movement, while reusing the key with different delta/reason fails without mutation. Enforce append-only movement records; corrections use a new reversing adjustment. General variant edits cannot write on_hand directly. Later reservations are separate allocations, not an untraceable free-form stock edit.
- Merchandise publication requires a valid child record, at least one active variant, price/currency and collection information. Zero available stock can remain visible with an unavailable state; it cannot imply an accepted order. Never publish an incomplete mixed type by changing `listing_kind` on an existing venue.
- Sellers can move an item to draft, archive it, and restore an archived item as a draft without losing variants or stock history. Restoration never clears a platform takedown. Owned-photo removal is confirmed, tenant/listing-key validated, and invalidates copied media endpoint URLs.
- Public DTOs expose only approved catalog/brand fields and approved public media. Do not serialize the full Shop or Tenant model, verification documents, tax/business evidence or member identifiers.
- Media: retain the listing media relation, but store all new merchandise image objects privately, even for public listings. Serve them through an authorised merchandise-media endpoint that checks current listing publication, seller/catalog state and viewer access on every request; owner draft previews require seller permission. Return private/no-store responses and never expose storage keys or long-lived public/remote URLs. StoreListingMedia URL generation must select this endpoint for merchandise while preserving venue URLs. On a public→members/archive/feature-off transition, old endpoint URLs must deny new unauthorised reads. Previously downloaded copies cannot be recalled; do not promise otherwise. Use a dedicated commerce-media-local private disk for local/test storage and the existing s3 disk with private visibility in production, with tenant-scoped commerce-media object keys. Add nullable private disk/MIME/byte-size/checksum metadata to StoreListingMedia without rewriting venue rows. Accept JPEG/PNG/WebP only, maximum 5MB each and eight photos per listing; charge the existing tenant storage allowance under the tenant lock via StorageMeter, including private merchandise bytes in usage accounting. Roll back/delete a newly stored object if metadata persistence fails. Validate actual image type/ownership and reject arbitrary remote URL fields or SVG uploads. No public evidence documents.

## 4. Visibility and safe legacy integration

**Default safe reads:** existing generic listing queries must not expose members-only, archived or incomplete merchandise. Add a merchandise visibility scope to StoreListing that leaves venue/rental/service behavior unchanged and only admits public, published, non-archived, complete, not-taken-down merchandise from an active Shop/tenant with commerce_catalog enabled into anonymous reads. Feature revocation must apply to generic query/count/photo/MCP paths, not just the new controller. Explicit buyer/owner access helpers may bypass that scope only after verified membership/tenant ownership is established. Keep `StaffOnlyScope` and its controlled bypasses separate and intact.

**Seller access:** commerce routes resolve listing/variant IDs under the current tenant's Shop after `manage store catalog` authorisation; a bare unscoped route-model binding is not sufficient. Owner reads can include their private/archived merchandise without exposing another tenant's records. Existing venue CRUD must reject merchandise IDs and must not edit/delete type-specific stock. Retain existing rental/service records and legacy behavior until their own integration; do not hide unrelated records as a shortcut. Exclude merchandise from legacy venue administration lists, staff room selection/booking and event-venue attachment. Reject it in generic venue/supplier RFQ creation and checkout so those paths cannot bypass commerce_checkout. Guard legacy media actions so they cannot publish a merchandise photo to public storage. Reused venue search must exclude merchandise even for all-kind/category filter combinations; preserve supported rental/service searches rather than indiscriminately forcing every old query to venue-only.

**Buyer access:** public listing DTOs are available only for enabled catalog tenants and public/published/non-archived merchandise. For member products, require existing live email-first identity plus active access to a member of the selling tenant via `MemberAccess`. For the proposed S1 default, require an active self membership at the verified email; representative or phone-only purchase eligibility is deferred rather than inferred from document access. Re-evaluate access on each protected read and checkout. Deny inactive/exited memberships, changed member emails and expired email proof. Phone-credential revocation alone does not revoke a still-valid matching email identity; distinguish those tests rather than treating every credential change as email revocation. Unauthorized requests must not reveal private title, SKU, price, stock or existence through search/counts/photos. Show a generic verification/membership prompt from a public entry point rather than leaking a hidden item.

**Entry points and routes:** add merchandise-aware listing/detail links within the existing storefront and a Store link in organisation/Community navigation when enabled. Proposed public merchandise detail route `/marketplace/items/{slug}`; current `/marketplace/venues/{slug}` URLs keep working. Do not send merchandise cards to a venue detail endpoint. Existing venue search/home remains venue-oriented until a reviewed mixed catalog filter is added; the Shop storefront can group offerings by type with correct links.

**Rollout:** `commerce_catalog` allows catalog administration/discovery; `commerce_checkout` separately permits purchase checkout only after S1b acceptance. Later rental/venue/service transaction activation remains independent. Follow the current tenant feature/permission propagation patterns; do not change plan prices, commission terms or other tenant flags. Permission `manage store catalog` is distinct from `manage venue`, finance/refunds and collection. A new feature flag defaults off. Authorised catalog onboarding may create a missing Shop in a POST under the tenant lock; GET does not mutate data, and an inactive existing Shop is not silently reactivated. Public reads additionally require that Shop to be active. Local QA is authorised; production rollout is not.

## 5. S1b purchase contract (not implemented in S1a)

Propose one seller per order, GHS, collection-only and a 10-minute checkout quote/stock hold. These remain subject to provider timing and owner review. Price, membership eligibility, fee bearer/cap/rate and settlement/account identity are frozen server-side when a valid quote is accepted. Client totals, quantities, tenant IDs or gateway references never determine fulfilment.

Serialize the last-item check/reservation using the variant/stock owner lock; reserve exactly once per quote. Abandonment/failure/expiry releases once. A successful verified capture consumes the reservation once and creates the corresponding immutable stock movement; a competing buyer cannot consume the same units. Catalog corrections cannot reduce stock below active reservations after S1b is enabled.

Track each payment attempt/reference uniquely with recoverable states. Callback and webhook call the same verifier/confirmer; wrong account/currency/amount/metadata, duplicates, concurrent delivery, metadata strings, late or extra captures and lost responses are explicit cases. A late payment without stock must be recorded and reconciled/refunded, not discarded or used to oversell. Ledger failure cannot disappear behind a paid flag. Receipt creation/delivery is deduplicated and retryable without reissuing the order.

Before implementing checkout, approve the store fee policy, supported tenant settlement modes, refunds and seller payout/reconciliation ownership. Extend the existing fee-resolution rules by transaction context while preserving superadmin control, explicit zero waivers, caps and stored terms. Do not copy the old marketplace 10% or force every tenant to the platform account. Existing venue callbacks/payment paths stay on their current integration during S1; improvements are planned separately.

## 6. S1c collection, cancellation and support

Propose fulfilment states awaiting preparation → ready for collection → collected; use separate verified handover proof, not an event admission QR. Collection is auditable and idempotent. A wrong organisation/operator cannot read or collect an order. Order-history access follows live identity/member grants; shared phones do not grant history.

Include unpaid cancellation and staff-controlled full refund for paid, uncollected orders. Restock only when the approved cancellation/refund state warrants it; reconcile the provider/ledger result and repeated staff attempts. Lost provider responses must park in a visible review state, not trigger another transfer/refund. Partial refunds, collected-order returns and exchanges need an approved policy before expansion. Disclose collection location/hours, contact, order status and support rules.

## 7. Venue preservation and extension acceptance

Keep existing venue listing/booking IDs, public URLs, media, amenities, capacities, calendar holds/blackouts, enquiries/quotes/deposits, event linkage, tasks/inspections, staff-only rooms and host/planner operations. No destructive type conversion, historical reprice, forced gateway change, duplicate calendar or broad rollout.

Before any new shared adapter handles venue transactions, require compatibility tests for existing booking/payment continuation, staff/public boundaries, simultaneous public/internal reservation writers, cancelled/expired holds, messages/event links and ledger recovery. Later rentals add date-range quantity/asset reservations and return buffers/condition rules; later services add availability, approval/scope, milestones and completion. Mixed-type checkout stays deferred until its reservation/approval dependencies are designed.

## 8. Screen and interaction requirements

Use existing React/Inertia public/console tokens, square surfaces and light/dark states. Existing Metronic/Blade instructions do not replace the current React console patterns. No package additions.

- Storefront: organisation identity, offering-type labels, member visibility, product image/price/available options and unavailable states; correct venue links retained.
- Item: image, options, price, quantity and availability; collection terms; verification/access prompt; no live purchase button in S1a.
- Seller catalog: type-aware listing table, create/edit merchandise form, variant inventory, draft/public/member/archive states, stock history; no venue form fields on a shirt.
- Order screens (S1b/c): explicit amount breakdown/collection details, payment state distinct from fulfilment, retry/review states, accessible receipt/history and ready/collected handover controls.
- Mobile: readable 320px layouts, adequate touch targets, non-overlapping form labels, keyboard-operable options/dialogs, focus return, enlarged text and dark-mode contrast. Loading, empty, disabled and validation/error states are first-class acceptance cases.
- Preview uses synthetic offerings and illustrative artwork. Interactions demonstrate concepts only; they never charge money, reserve production stock, create live orders or collect private identity.

### Safe rollback to older application code

A release predating the merchandise visibility scope does not understand the catalog flags or member-only child visibility. Before any authorised rollback to that code, move every merchandise **parent** listing to `draft` and pause catalog entry points. Turning a flag off or archiving only the child is insufficient for older generic listing queries. Retain catalog, variant and immutable stock records; do not drop these tables to roll back source. Verify public storefront/detail/media reads after the rollback. This is an operational deployment gate, not an action performed during local implementation.
